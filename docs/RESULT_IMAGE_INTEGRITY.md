> Статус: исторический разбор от 01.08.2026. ## Короткий вывод

Сервер авторитетно проверяет игровой прогресс: в `POST /colorings/:id/progress/actions` принимаются только отдельные действия до 64 клеток, цвет сверяется с `template.cells`, а состояние сохраняется с CAS по `revision`. Поэтому нельзя просто отправить `completed: true` или заменить всю карту прогресса через старый `PUT /colorings/:id/progress`.

При этом итоговая картинка хранится иначе. Клиент сам генерирует PNG и отправляет его как `resultDataUrl`; сервер проверяет только форму data URL, размер и PNG-signature, а затем записывает присланную строку в `artworks.image_url`. Сервер не декодирует пиксели, не сравнивает их с `template.cells` и не генерирует canonical-изображение сам. Это отдельный риск целостности контента: можно пройти валидный прогресс, но приложить к завершению другой корректный PNG.

Текущий статус: **частично защищено / ограничение целостности контента остаётся открытым**. Для MVP это не даёт доступа к чужим данным и не позволяет завершить раскраску без корректных действий, но позволяет подменить визуальное доказательство результата и опубликовать его через обычный пользовательский поток.

## Фактический поток данных

```text
Пользовательский Canvas
        │
        │ filled → diff changes; при полном заполнении renderCompletedImage()
        ▼
src/lib/progressSaveQueue.js
        │  resultDataUrl = getResultDataUrl(snapshotFilled)
        ▼
src/App.jsx
        │  POST /colorings/:id/progress/actions
        │  { changes, revision, resultDataUrl }
        ▼
server/routes/colorings.js
        │  validateChanges() + CAS + isComplete()
        │  validateResultDataUrl() — только формат PNG
        ▼
artworks.image_url (SQLite/PostgreSQL)
        │
        ├── POST /posts/create — проверяет owner и is_completed
        └── feed/profile — отдаёт artwork.image_url
```

## Что именно может сделать атакующий

Модель угроз предполагает уже авторизованного пользователя. Telegram подпись и пользовательская авторизация в рамках этого риска считаются отдельной границей и не обходятся данным сценарием.

1. Получить доступную публичную раскраску и её корректный `template.cells`.
2. Отправить через `POST /colorings/:id/progress/actions` правильные действия, разбитые на батчи до 64 клеток. Это можно сделать напрямую скриптом, без UI; сервер это намеренно принимает как игровое API.
3. На последнем запросе приложить любой PNG, который проходит `validateResultDataUrl` (например, однотонный или изображение другого проекта), размером не более 500 000 символов.
4. После ответа с `artwork_id` вызвать штатный `POST /posts/create`.
5. В ленте и профиле будет показан сохранённый присланный PNG, хотя серверный progress соответствует другой раскраске.

Это не позволяет:

- объявить раскраску завершённой одной подменой `percent` или `completed` — таких входных полей сервер не использует;
- записать произвольные цвета в карту через одно действие — `change.color` сравнивается с `template.cells[index]`;
- опубликовать чужой artwork — `posts.js:35` требует совпадения `artwork.owner_id` и `req.userId`;
- получить чужой private template через этот endpoint — `canRead()` проверяет visibility и owner.

Важно различать две вещи: **целостность прогресса** сейчас частично авторитетна, а **целостность финального пиксельного изображения** — нет.

## Почему проверка PNG или hash не решает задачу

Текущая PNG-проверка отвечает только на вопрос «похоже ли тело на PNG». Она не отвечает на вопросы:

- совпадают ли ширина и высота с шаблоном;
- соответствует ли цвет каждой клетки `template.cells` и `filled`;
- не содержит ли изображение чужой результат;
- применён ли тот же алгоритм рендера, что используется в продукте.

Хэш клиентского файла тоже не доказывает правильность. Хэш подтверждает лишь неизменность конкретных байтов после того, как они были выбраны клиентом. Злоумышленник может заранее вычислить SHA-256 для своего подменённого PNG и отправить пару «файл + его честный hash». Нужен не hash произвольного клиентского файла, а серверно полученный canonical output или независимая серверная проверка его содержимого.

## Варианты решения

### Вариант A — оставить как MVP-ограничение

Оставить текущий протокол и явно считать `resultDataUrl` клиентским preview, а не доказательством результата.

Плюсы:

- нет миграций и изменений API;
- текущий UI, download/share и публикация продолжают работать;
- минимальный риск регрессии.

Минусы:

- подменённое изображение можно опубликовать;
- moderation и пользователи видят результат, которому сервер не доверяет;
- при росте сетки data URL и Canvas становятся узкими местами.

При выборе этого варианта нужно как минимум зафиксировать ограничение в документации и не использовать `artwork.image_url` как доказательство честного прохождения.

### Вариант B — усилить клиентскую валидацию или hash

Клиент может отправлять размеры, checksum и дополнительные метаданные, сервер — сверять их с ожиданиями.

Это может обнаруживать случайные ошибки или повреждённые запросы, но не является полноценной защитой: весь клиентский payload, включая checksum, контролируется пользователем. Вариант годится только как диагностика/совместимость, не как security boundary.

### Вариант C — серверный canonical render (рекомендуемое направление)

Сервер хранит шаблон и авторитетный progress, а при переходе в completed сам строит результат из `template.cells`, подтверждённой карты и палитры. `resultDataUrl` либо игнорируется для artwork, либо сохраняется отдельно как необязательный client preview.

Плюсы:

- источник истины находится на сервере;
- подменённый PNG не может изменить опубликованный результат;
- можно единообразно контролировать размеры и палитру.

Минусы и границы:

- нужен серверный rasterizer (например, библиотека PNG или другой безопасный renderer);
- для больших сеток CPU, память и время рендера должны быть ограничены;
- потребуется решить, где хранить binary result и как повторять неуспешный render.

### Вариант D — асинхронный worker/on-demand render

Разновидность варианта C: completion создаёт artwork со статусом `render_pending`, а worker строит изображение и кладёт его в локальное или S3-compatible storage. Публикация разрешается только после успешного render.

Подходит для 500×500 и выше, если синхронный HTTP-запрос становится долгим. Требует очереди/worker, статусов, retry, очистки orphan-файлов и наблюдаемости; это не следует добавлять до измерения реального предела сетки.

## Связь с большими сетками

Текущая реализация создаёт обычные JavaScript-массивы `cells`/`filled`, хранит их в JSON и рисует итоговый Canvas с `pixelSize = 16`. Ниже — расчёт порядка величин для квадратной сетки; это оценка размера текущих структур, а не результат production-бенчмарка.

| Сетка | Клеток | `filled` JSON (пустой, примерно) | Canvas результата | Только RGBA-buffer Canvas* |
|---:|---:|---:|---:|---:|
| 160×160 | 25 600 | 75 KB | 2 560×2 560 | 0,024 GiB |
| 256×256 | 65 536 | 192 KB | 4 096×4 096 | 0,063 GiB |
| 384×384 | 147 456 | 432 KB | 6 144×6 144 | 0,141 GiB |
| 500×500 | 250 000 | 750 KB | 8 000×8 000 | 0,238 GiB |
| 768×768 | 589 824 | 1,77 MB | 12 288×12 288 | 0,563 GiB |
| 1 024×1 024 | 1 048 576 | 3,15 MB | 16 384×16 384 | 1,000 GiB |
| 1 200×1 200 | 1 440 000 | 4,32 MB | 19 200×19 200 | 1,373 GiB |

\* Без учёта внутренних копий Canvas, PNG-кодирования, React state, `cells`, `filled`, зон и временных массивов.

Фактические узкие места:

- `server/routes/colorings.js:132-139` сериализует/десериализует полный `filled_json`;
- `server/routes/colorings.js:58-62` возвращает полный `cells` массив в detail endpoint;
- `server/routes/colorings.js:227-240` возвращает индексы зон;
- `src/App.jsx:361-362`, `:427-432`, `:448-462` регулярно копируют большие массивы при painting/undo/redo;
- `src/lib/pixelColoring.js:24-36` делает полный проход по всем клеткам и создаёт большой Canvas;
- `src/lib/pixelColoring.js:233-252` выполняет вложенный sampling по исходным пикселям;
- `src/lib/pixelColoring.js:61-127` (сглаживание/очистка регионов) и `:235-277` (sampling/edge-aware smoothing) обходит сетку и создаёт дополнительные структуры;
- `src/features/coloring/ColoringCanvas.jsx:37-114` ограничивает рисование видимой областью, что помогает интерактивности, но не уменьшает размер `cells`/`filled` и финального Canvas.

Для 1200×1200 итоговый Canvas шириной 19 200 пикселей уже выходит за распространённый безопасный диапазон размеров Canvas; конкретный лимит зависит от браузера и устройства. Поэтому повышение серверного лимита с 160 до 1200 само по себе не делает сценарий рабочим.

Отдельный реальный-image benchmark `01.08.2026` уточнил картину: `buildColoringFromImage` для `neon-cat.png` занял около `3,15 с` на `1200×1200`, но только построение `createWorkingWindows` заняло около `17,7 с` в headless Chromium. Это не полный пользовательский runtime и не mobile/WebView SLA, однако подтверждает, что server-side canonical render нельзя проектировать отдельно от оптимизации клиентского engine и асинхронного завершения для больших сеток.

## Рекомендуемое направление

До достижения измеренного предела сетки не следует одновременно менять формат прогресса и изображений. Практический порядок:

1. Зафиксировать текущий контракт: `resultDataUrl` — необязательный клиентский preview; `filled` и completion — серверная истина.
2. Добавить отдельный негативный API-тест (в будущем, когда будет разрешено менять тесты): корректные completion changes + PNG, заведомо не соответствующий шаблону, не должен становиться canonical artwork.
3. Провести benchmark 160, 256, 384, 500, 768, 1024 и 1200 на desktop и mobile, измеряя creation, detail load, first render, one-cell paint, complete/save, reopen и publish.
4. Если целевой диапазон остаётся ≤160/256, выбрать синхронный server-side render при completion.
5. Если нужен диапазон 500+, вынести canonical render из HTTP request в worker или on-demand job; binary result хранить в private/object storage и публиковать только после успешной генерации.
6. После выбора формата обновить API-документацию и `PROJECT_MAP`/security findings; до этого не объявлять риск resolved.

### Критерии приёмки будущего исправления

- Сервер сам получает canonical image из авторитетных `template.cells`, `palette` и progress; клиентский PNG не определяет содержимое artwork.
- Запрос с корректным progress, но подменённым PNG либо отклоняется, либо PNG игнорируется и заменяется серверным результатом.
- Повторный completion идемпотентен и не создаёт второй artwork.
- Публикация разрешена только после успешного canonical render.
- Размер, формат, palette и отсутствие лишних пикселей проверяются на сервере.
- Для 160×160, выбранного промежуточного размера и целевого максимума есть integration/E2E или environment-тесты с негативным сценарием.
- Ошибка/timeout renderer не оставляет опубликованный пост с неподтверждённым `image_url`; есть retry/cleanup для временных объектов.
- В staging проверены PostgreSQL, S3/MinIO, reverse proxy и Telegram-поток; локальный unit-тест сам по себе не считается environment validation.

## Что можно проверить локально и что требует staging

### Локально

- Сервер отклоняет malformed/non-PNG/слишком длинный data URL (`validateResultDataUrl`).
- Сервер принимает корректный progress только при правильных index/color/revision.
- Ручной API-запрос с валидным, но чужим PNG демонстрирует текущую проблему: artwork создаётся с присланным `image_url`.
- Размер JSON и время обработки для разных сеток можно измерить через local API и Playwright.
- При Docker доступны PostgreSQL и MinIO integration checks, но они не меняют доверие к result PNG.

### Только staging/production-like окружение

- Реальные Canvas limits и memory pressure конкретных Telegram WebView/мобильных устройств.
- Стабильность PNG generation/upload за HTTPS reverse proxy.
- Поведение S3-compatible storage, orphan cleanup и приватных объектов.
- Telegram Mini App lifecycle (pagehide, suspend/resume, back button) при завершении и публикации.
- Backup/restore binary artwork вместе с PostgreSQL.

## Решение для текущего этапа

Пока benchmark больших сеток и выбор формата не завершены, оставляем код без изменений и не считаем риск закрытым. Для текущего MVP его нужно формулировать так:

> Сервер защищает целостность карты прогресса, но доверяет клиентскому PNG при создании artwork. Это приемлемо только как временное ограничение доверия к опубликованным пользовательским изображениям; для production canonical artwork должен генерироваться или независимо проверяться на сервере.
