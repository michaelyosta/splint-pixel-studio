# План увеличения сетки раскрашивания

Дата фиксации: 03.08.2026  
Проверяемый checkout: `release/public-alpha-rc1`, commit `7246358dd4fc958f8780ff24a7f8c1b617979e79`  
Для сравнения: `origin/main` на момент проверки — `68d751e1da35de3bfd92f6bec382f0af830ac502`.

## Краткий вывод

Текущий предел `160×160` — не случайная константа. Главный предел задаёт не сам Canvas, а сочетание трёх решений: `cells` и `filled` хранятся как полные JavaScript-массивы, `ColoringSession` пересчитывает рабочие окна при изменении прогресса/цвета, а `createWorkingWindows` для каждого окна снова проходит весь кластер. При одном большом кластере это даёт примерно квадратичный рост работы.

Наилучший путь — поэтапная гибридная архитектура: сначала сохранить текущий продуктовый контракт и убрать повторные проходы через пространственный индекс/однопроходную генерацию окон, одновременно сделать worker-путь действительно worker-safe; затем, если целевая детализация выше примерно `512×512`, перейти к тайлам и виртуализированному Canvas. Поднимать официальный лимит до завершения этих этапов нельзя.

## Варианты архитектуры

### Вариант A — оптимизация текущего движка

Сохранить текущие `cells`/`filled`, API и историю прогресса, но:

1. заменить повторный `window × cluster` проход в `workingWindows.js` однопроходной раскладкой по spatial buckets/row spans;
2. кэшировать кластеризацию и инвалидировать только изменённые области;
3. хранить рабочие буферы в `Uint8Array`/`Int16Array`, а JSON собирать только на границе API;
4. вынести image-to-template и тяжёлую кластеризацию в worker без DOM API — preview должен строиться в main thread или через `OffscreenCanvas` с проверенным fallback;
5. ограничить React state крупными объектами: прогресс и история должны обновлять только изменённые диапазоны.

Плюсы: небольшая миграция, сохранение текущего progress/API, низкий риск для `160×160`. Минусы: полная сетка всё равно остаётся в памяти и в сетевом DTO; после примерно `512×512` мобильный потолок остаётся неопределённым.

### Вариант B — тайлы, виртуализация и LOD

Сохранить логические координаты ячеек, но разделить их на тайлы (например, `32×32` или `64×64`): worker строит тайлы и индекс регионов, Canvas загружает только видимые тайлы плюс соседний prefetch, а zoom использует LOD/thumbnail. Прогресс передаётся delta/chunk-запросами и хранится по тайлам; старые массивы конвертируются при чтении.

Плюсы: память и Canvas-work становятся пропорциональны viewport, а не всей картинке; это единственный реалистичный путь к `768–1200` на мобильном. Минусы: существенная миграция API/хранилища, сложнее undo/reveal/achievements, нужны версии формата и тщательные тесты сохранения/конфликтов.

### Сравнение

| Критерий | Вариант A | Вариант B |
|---|---|---|
| Реалистичный первый target | `256–512` после профилирования | `512–1200` после миграции |
| Изменения API/данных | минимальные | значительные, нужны tile/chunk contracts |
| Риск регрессии текущей игры | низкий/средний | высокий |
| Мобильный UX | улучшится, но потолок не доказан | лучший потенциал |
| Время до проверяемого результата | короче | дольше |
| Рекомендация | обязательный этап 1 | этап 2, если SLO A не достигаются |

## Рекомендуемый путь и SLO

1. **Сначала A0: воспроизводимый benchmark.** Один и тот же real-image набор, desktop и настоящий/эмулированный Telegram WebView, измерения p50/p95: generation, first Canvas, first interaction, save/reopen, peak memory, event-loop latency.
2. **A1: однопроходные окна и typed buffers.** Не менять официальный лимит; доказать отсутствие квадратичного `window × cluster` прохода.
3. **A2: worker-safe pipeline.** Убрать DOM-зависимости из worker-модуля и добавить негативный тест, что UI не блокируется во время генерации.
4. **Gate A.** Только если desktop и mobile SLO выполнены, провести ограниченный эксперимент `256`/`384`/`512`.
5. **B1/B2 при необходимости.** Если `512` не укладывается в SLO или требуется `768+`, внедрять тайлы, LOD и chunked progress с миграцией старых массивов.

Предлагаемые, пока не подтверждённые SLO для публичного сценария:

- generation p95 ≤ 3 s на desktop и ≤ 6 s на целевом mobile WebView;
- first interactive Canvas p95 ≤ 2 s после получения шаблона;
- длительная работа без event-loop пауз > 100 ms;
- peak JS heap ≤ 180 MB на mobile и ≤ 300 MB на desktop;
- save/reopen p95 ≤ 1 s при delta-запросе;
- никаких новых зависаний/потери прогресса в 30-минутной сессии.

Эти значения — критерии принятия решения, а не текущие результаты.

## Что пока не доказано и статус

- Свежий browser benchmark на release commit `7246358` — **не выполнен**.
- Фактический `Worker` success/fallback (`document is not defined`) — **не воспроизведён в браузере**.
- Поведение на реальном Telegram WebView, iOS/Android и устройствах с ограниченной памятью — **не проверено**.
- Полный flow `create → API → Canvas → save → reopen` для сеток выше `160` — **не подтверждён**.
- Безопасный формат миграции массива прогресса в tiles/chunks — **не спроектирован на уровне контракта**.

Поэтому текущий статус исследования: **design recommendation готова, measurement gate заблокирован отсутствием свежего запуска и мобильной среды**. Следующий конкретный шаг — выполнить изолированный benchmark из `docs/GRID_BENCHMARK.md` на commit `7246358`, затем принять или отклонить Gate A по SLO; официальный лимит до этого оставить `160×160`.
