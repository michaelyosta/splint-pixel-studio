# Benchmark больших сеток

Дата проверки: 01.08.2026  
Checkout: `main` + существующая незакоммиченная рабочая копия  
Commit исходного кода: `782110afe05bb98936afd64a96c74171f658b306`

## Краткий вывод

В основной ветке сервер и миграции разрешают пользовательские сетки только до `160×160`. Этот предел подтверждён существующим Playwright-сценарием, который создаёт, сохраняет и открывает раскраску `160×160` (`e2e/creator.spec.js`, тест `6b`), а также API-интеграционным тестом, принимающим `160×160` и отклоняющим `161×161` (`server/test/api.integration.test.js`).

Сетки `256×256`, `384×384` и `512×512` были проверены в изолированном browser harness с синтетическим шаблоном и замоканным API, а также отдельным прогоном реального `neon-cat.png`. Это измеряет клиентский renderer и route-targeting, но не является подтверждением поддержанного продуктового сценария: текущий `POST /colorings/create` их отвергнет.

Для `768×768` синтетический сценарий не дождался появления Canvas за 15 секунд. В отдельном безопасном прогоне реального изображения этапы генерации `cells` и построения working windows завершились и для `1200×1200`, но это не полный пользовательский поток: не проверялись API, React-сессия, Canvas interaction, мобильный WebView и сохранение. Поэтому 500/1200 всё ещё нельзя называть рабочими.

## Что именно проверялось

Временный Playwright-скрипт (вне репозитория) запускал Vite на `127.0.0.1:5188` и подменял только `/api/*` ответами. Для каждого размера он:

1. открывал `/?coloring=bench`;
2. передавал в React шаблон с `width × height` и `cells` длиной `width*height`;
3. ждал появления `canvas[data-template-width]` и инициализации route-targeting;
4. выполнял один клик по Canvas;
5. ждал сохранение через `POST /colorings/:id/progress/actions`;
6. перезагружал страницу и проверял повторное открытие.

API-мок не менял исходный код, базу, тесты или конфигурацию. Время — wall-clock в headless Chromium, viewport `1280×900`, device scale factor `1`; `performance.memory` доступен только как ориентировочный показатель V8 heap.

## Реальное изображение: обработка и working windows

01.08.2026 отдельный временный Playwright harness обработал реальный файл `public/assets/catalog/neon-cat.png` (PNG, `1 097 868` байт). Для каждого размера создавался новый headless Chromium с viewport `1280×900`; API и PostgreSQL не использовались. В таблице `build` — полный `buildColoringFromImage`, `clusters` — `findUnfilledClusters`, `windows` — `createWorkingWindows` для крупнейшего незаполненного кластера и viewport `1280×640`.

Это важное уточнение к первоначальному synthetic timeout: базовая обработка реального файла сама по себе не является мгновенным отказом даже на `1200×1200`, но 17,7 секунды только на working windows — уже неприемлемая задержка до полноценного игрового интерфейса. Значения heap — ориентир Chromium, а не лимит Telegram WebView.

В том же прогоне фактическая сериализация одного объекта создания составила примерно `1,54 MB` для `160×160`, `2,02 MB` для `512×512` и `4,37 MB` для `1200×1200` (включая `cells`, `previewDataUrl` и `originalDataUrl`). Это ниже текущего JSON body limit `15 MB`, но не учитывает proxy limits, мобильную память, concurrent requests и полный React flow.

## Оценка размеров данных

Текущая модель хранит `cells` и progress как JSON-массивы обычных JavaScript-чисел (`server/routes/colorings.js`, `progressPayload`; `src/lib/progressSaveQueue.js`). Для простого худшего случая с нулевыми `cells` и `-1` в `filled` длина JSON получается:

| Сетка | Клеток | `cells` JSON | `filled` JSON | Вместе без обвязки |
|---:|---:|---:|---:|---:|
| 160×160 | 25 600 | 50.0 KB | 75.0 KB | 125.0 KB |
| 256×256 | 65 536 | 128.0 KB | 192.0 KB | 320.0 KB |
| 384×384 | 147 456 | 288.0 KB | 432.0 KB | 720.0 KB |
| 512×512 | 262 144 | 512.0 KB | 768.0 KB | 1.25 MB |
| 768×768 | 589 824 | 1.12 MB | 1.69 MB | 2.81 MB |
| 1 024×1 024 | 1 048 576 | 2.00 MB | 3.00 MB | 5.00 MB |
| 1 200×1 200 | 1 440 000 | 2.75 MB | 4.12 MB | 6.87 MB |

Это только массивы. Создание использует также `previewDataUrl`, `originalDataUrl` и JSON-обвязку; сервер ограничивает body через `express.json({ limit: '15mb' })` (`server/index.js`) и preview PNG — 300 000 символами (`server/routes/colorings.js`). При текущем лимите `160` эти оценки не создают проблем, но они не доказывают возможность безопасной загрузки изображения 1200×1200.

## Серверные границы

- `server/routes/colorings.js`: `POST /colorings/create` принимает только `8…160` по каждой стороне.
- `server/migrations/009_max_grid_160.sql` и `server/migrations/sqlite/009_max_grid_160.sql` задают SQL-ограничение `8…160`.
- `server/test/api.integration.test.js`: `160×160` принимается, `161×161` отклоняется.
- `e2e/creator.spec.js`, тест `6b`: реальный пользовательский поток `160×160` — расчёт preview, сохранение, GET шаблона и открытие Canvas.
- `src/features/coloring/ColoringCanvas.jsx`: рендер ограничен видимой областью Canvas, но `ColoringSession` предварительно строит кластеры и working windows по полным массивам.

## Что можно утверждать сейчас

1. `160×160` — единственный максимальный размер, подтверждённый и клиентским E2E, и серверными проверками.
2. `256…512` — экспериментально воспроизводимы только в mocked frontend harness; они не поддерживаются текущим API и миграциями.
3. `768×768` уже не достиг синтетической инициализации Canvas за 15 секунд; это не равно доказанному crash, но является достаточным сигналом риска.
4. Для `1 024×1 024` и `1 200×1 200` подтверждена только обработка изображения и построение engine windows в изолированном headless harness; полный runtime-поток не проверен и не должен называться рабочим.
5. Изменять лимиты или выбирать архитектуру для 1200 без профиля реального изображения, мобильного устройства и production-like API преждевременно.

## Следующий безопасный эксперимент

Перед расширением лимита нужен отдельный benchmark-профиль, не в обычной рабочей копии:

1. изолированное устройство/профиль Chromium с фиксированным лимитом памяти и записью trace;
2. реальные изображения, а не только один однородный кластер (мелкие фрагменты, много цветов, worst-case один регион);
3. отдельные этапы: `buildColoringFromImage`, JSON POST `/colorings/create`, route-targeting, Canvas interaction, save/reopen;
4. жёсткие stop conditions по RSS, event-loop latency, timeout, body size и `413`;
5. desktop и настоящий Telegram WebView/мобильный профиль;
6. только после измерений — выбор оптимизации (TypedArray/chunks/worker/tiles/server-side render).

Пока этот эксперимент не проведён, продуктовый лимит следует оставить `160×160`, а 500×500 и 1200×1200 считать исследовательскими целями, а не реализованными возможностями.

## Ограничения отчёта

- Browser harness использовал mock API и не проверял PostgreSQL, S3/MinIO или сетевой latency.
- Не проводилась реальная Telegram Mini App проверка.
- `performance.memory` Chromium не является межбраузерным или мобильным SLA.
- Полный пользовательский runtime benchmark 500/1200 (API → React-сессия → Canvas → сохранение/reopen) не запускался; выполнены только изолированные этапы обработки реального изображения и engine windows. Для полного прогона нужен отдельный изолированный desktop/mobile профиль.
- Исходный код, тесты, зависимости, конфигурация и Docker-файлы в рамках benchmark не изменялись.
